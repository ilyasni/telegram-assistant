## 2. АНАЛИЗ ПАРСИНГА

### Парсер работает, но не находит новых сообщений

**Примеры из логов:**

   - `since_date`: `2026-01-16T16:44:08.531256+00:00`
   - `last_post_date`: `2026-01-16T16:42:01+00:00` (последний пост в БД)
   - `messages_processed`: 0
   - `messages_skipped`: 1
   - `max_message_date`: `2026-01-16T16:42:01+00:00`
   - **Проблема**: Парсер запросил сообщения с `16:44:08`, но получил сообщение с `16:42:01` (старое), пропустил как дубликат

2. **Канал "О Бизнесе"** (`4791c699-a07d-439d-9d74-e5506fddcfbf`):
   - `since_date`: `2026-01-16T16:44:36.499990+00:00`
   - `last_post_date`: `2026-01-16T16:20:12+00:00`
   - `messages_processed`: 0
   - `last_parsed_at`: `2026-01-16 17:12:08 UTC`

### Логика since_date

Парсер использует:
1. **Приоритет 1**: `last_parsed_at - overlap` (10 минут overlap)
2. **Приоритет 2**: `last_post_date` (если `last_parsed_at` слишком старый)

**Пример расчета:**
```
base_date = last_parsed_at = 2026-01-16T16:54:08.531256+00:00
since_date = base_date - 10 minutes = 2026-01-16T16:44:08.531256+00:00
```

Парсер запрашивает сообщения **после** `since_date`, но Telegram API может вернуть сообщения до этой даты.

## 3. ВОЗМОЖНЫЕ ПРИЧИНЫ

### ✅ Возможная причина 1: В каналах просто нет новых сообщений

**Анализ:**
- Последний пост был 27 минут назад
- Парсер работает и запрашивает сообщения
- Но `messages_processed: 0` — значит новых сообщений нет

**Вывод**: Возможно, в каналах просто тишина — нет новых постов.

### ⚠️ Возможная причина 2: Telegram API не возвращает новые сообщения

**Проблема:**
- Парсер запрашивает сообщения с `since_date = 16:44:08`
- Но Telegram API может вернуть сообщения только до `16:42:01` (старые)
- Все новые сообщения пропускаются как дубликаты или не возвращаются

**Проверка:**
- Нужно проверить, действительно ли есть новые сообщения в каналах
- Возможно, Telegram API имеет задержку или ограничения

### ⚠️ Возможная причина 3: Проблема с логикой overlap

**Проблема:**
- Парсер использует `since_date = last_parsed_at - 10 минут`
- Но если `last_parsed_at` обновляется даже без новых постов, `since_date` смещается вперед
- Новые сообщения между `last_post_date` и `since_date` могут быть пропущены

**Пример:**
```
last_post_date = 16:42:01 (последний пост в БД)
last_parsed_at = 16:54:08 (время последнего парсинга)
since_date = 16:44:08 (last_parsed_at - 10 минут)

Если новый пост был в 16:43:00, он может быть пропущен,
так как парсер запрашивает сообщения после 16:44:08.
```

## 5. ПРОВЕРКА

### Команды для диагностики

```bash
# Проверить последние посты
docker compose exec -T supabase-db psql -U postgres -d postgres -c "
  SELECT c.title, MAX(p.created_at) as last_post, COUNT(*) as posts_count
  FROM channels c
  LEFT JOIN posts p ON p.channel_id = c.id
  WHERE p.created_at > NOW() - INTERVAL '24 hours'
  GROUP BY c.id, c.title
  ORDER BY last_post DESC
  LIMIT 10;
"

# Проверить каналы с большим разрывом между last_post и last_parsed_at
docker compose exec -T supabase-db psql -U postgres -d postgres -c "
  SELECT 
    c.title,
    c.last_parsed_at,
    (SELECT MAX(p.posted_at) FROM posts p WHERE p.channel_id = c.id) as last_post,
    EXTRACT(EPOCH FROM (c.last_parsed_at - (SELECT MAX(p.posted_at) FROM posts p WHERE p.channel_id = c.id))) / 60 as gap_minutes
  FROM channels c
  WHERE c.last_parsed_at > NOW() - INTERVAL '1 hour'
  ORDER BY gap_minutes DESC
  LIMIT 10;
"

# Проверить логи парсинга
docker compose logs telethon-ingest --since 30m | grep -E "(messages_processed|since_date|last_post_date)"
```
