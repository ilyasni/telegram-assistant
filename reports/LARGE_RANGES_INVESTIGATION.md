# Исследование логики парсинга для больших диапазонов

**Дата**: 2025-12-03  
**Критичность**: ВЫСОКАЯ  
**Context7**: Анализ проблем с парсингом каналов с большими диапазонами message_id

---

## Проблема

### Пример проблемного канала

**Канал "Около Искусства" (okolo_art)**:
- **Диапазон message_id**: 1252 - 900003
- **Ожидается постов**: 898,752
- **Постов в БД**: 47
- **Покрытие**: 0.01%
- **Пропущено**: 898,705 постов

---

## Анализ текущей логики парсинга

### Лимиты запросов

**Incremental режим**:
- `limit = batch_size * 100 = 50 * 100 = 5,000` сообщений
- Парсит только последние 5,000 сообщений от `last_parsed_at`

**Historical режим**:
- `limit = batch_size * 200 = 50 * 200 = 10,000` сообщений
- Парсит последние 24 часа (настраивается через `PARSER_HISTORICAL_HOURS`)

### Проблемы для больших диапазонов

1. **Лимиты недостаточны**:
   - Для диапазона 898,752 постов лимит 10,000 сообщений покрывает только ~1.1%
   - Historical режим парсит только последние 24 часа
   - Старые посты не парсятся

2. **Historical режим ограничен временем**:
   - Парсит только последние 24 часа (по умолчанию)
   - Для канала с историей в несколько лет этого недостаточно

3. **Отсутствие backfill логики**:
   - Нет механизма для заполнения исторических пропусков
   - Нет автоматического обнаружения и заполнения gaps

## Текущая реализация

### Метод `_get_message_batches()`

**Лимиты**:
```python
limit = batch_size * 100 if mode == "incremental" else batch_size * 200
# incremental: 5,000 сообщений
# historical: 10,000 сообщений
```

**Фильтрация по времени**:
- **Historical**: парсит сообщения >= `since_date` (последние 24 часа)
- **Incremental**: парсит сообщения > `since_date` (новее `last_parsed_at`)

**Проблема**: Для канала с огромным диапазоном message_id это не покрывает историю.

## Рекомендации (Context7 Best Practices)

### 1. Увеличить лимиты для historical режима

**Проблема**: Лимит 10,000 сообщений недостаточен для каналов с большой историей.

**Решение**:
- Увеличить лимит для historical режима до 50,000-100,000 сообщений
- Или сделать лимит динамическим на основе оценки размера канала

**Реализация**:
```python
# Увеличенный лимит для historical режима
if mode == "historical":
    # Для больших каналов увеличиваем лимит
    limit = batch_size * 1000  # 50,000 сообщений
else:
    limit = batch_size * 100  # 5,000 сообщений (incremental)
```

### 2. Реализовать backfill для исторических gaps

**Проблема**: Нет механизма для заполнения пропущенных исторических постов.

**Решение**:
- Обнаруживать большие gaps в message_id
- Автоматически запускать backfill для заполнения gaps
- Использовать существующую логику из `history_replay.py`

**Реализация**:
```python
async def _detect_and_backfill_gaps(
    self,
    channel_id: str,
    min_message_id: int,
    max_message_id: int
):
    """
    Обнаруживает gaps и запускает backfill для их заполнения.
    """
    # Обнаружение gaps
    gaps = await self._detect_message_id_gaps(channel_id, min_message_id, max_message_id)
    
    # Запуск backfill для больших gaps
    for gap in gaps:
        if gap['size'] > 1000:  # Только большие gaps
            await self._backfill_gap(channel_id, gap)
```

### 3. Улучшить определение режима парсинга

**Проблема**: Каналы с большими gaps могут не переключаться на historical режим.

**Решение**:
- Автоматически переключать на historical режим при обнаружении больших gaps
- Использовать более агрессивные пороги для historical режима

**Реализация**:
```python
async def _decide_mode_with_gap_detection(
    self,
    channel: Dict[str, Any],
    channel_id: str
) -> str:
    """
    Определяет режим парсинга с учетом gaps в message_id.
    """
    # Проверяем наличие больших gaps
    gaps = await self._check_message_id_gaps(channel_id)
    
    if gaps and any(gap['size'] > 1000 for gap in gaps):
        # Большие gaps - используем historical режим
        return "historical"
    
    # Обычная логика определения режима
    return await self._decide_mode(channel)
```

### 4. Мониторинг покрытия каналов

**Проблема**: Нет автоматического обнаружения каналов с низким покрытием.

**Решение**:
- Использовать метрику `channel_coverage_percent`
- Автоматически запускать backfill для каналов с покрытием < 10%

**Реализация**:
```python
async def _monitor_channel_coverage(self, channel_id: str):
    """
    Мониторит покрытие канала и запускает backfill при необходимости.
    """
    coverage = await self._calculate_coverage(channel_id)
    
    if coverage < 10.0:  # Низкое покрытие
        logger.warning(
            "Low channel coverage detected, triggering backfill",
            channel_id=channel_id,
            coverage_percent=coverage
        )
        await self._trigger_backfill(channel_id)
```

## Контекстные ограничения Telegram API

### Ограничения `iter_messages()`

1. **Максимальный лимит**: Telegram API может ограничивать количество сообщений за один запрос
2. **Скорость запросов**: Rate limiting может замедлять парсинг больших диапазонов
3. **Время выполнения**: Парсинг 898,752 постов может занять дни/недели

### Рекомендации

1. **Использовать батчинг**: Парсить небольшими батчами (50-100 сообщений)
2. **Распределить по времени**: Парсить историю постепенно, не все сразу
3. **Приоритизировать новые посты**: Сначала парсить новые посты, потом историю
