## 2. АНАЛИЗ ЛОГОВ

### Парсер работает, но не находит сообщения

**Логи для banksta:**
```
"total_messages_checked": 20,
"total_messages_yielded": 0,
"found_newer_messages": false,
"since_date": "2026-01-16T16:44:08.531256+00:00"
```

**Проблема:**
1. Парсер проверяет только **20 сообщений** (`max_check_before_stop = 20`)
2. Если первые 20 сообщений старше `since_date`, парсер останавливается
3. Новые сообщения могут быть дальше в списке или Telegram API может не вернуть их сразу

### Логика фильтрации

**Текущая логика (строки 3136-3216):**
- В incremental режиме проверяет до 20 сообщений
- Если первые 20 сообщений <= `since_date`, останавливается
- Логирует `"no_newer_messages"` и завершает парсинг

**Проблема:** Telegram API может вернуть сообщения не сразу или в нехронологическом порядке.

---

## 3. ПРИЧИНА ПРОБЛЕМЫ

### Основная причина: Недостаточная проверка сообщений

1. **`max_check_before_stop = 20`** — слишком мало
   - Если канал публикует часто, новые сообщения могут быть дальше
   - Telegram API может вернуть до 100-500 сообщений за раз

2. **Telegram API может задерживать новые сообщения:**
   - При `iter_messages` без `offset_date` API возвращает последние сообщения
   - Но новые сообщения могут появиться с задержкой
   - Сообщения могут быть не в хронологическом порядке

3. **Фильтрация слишком строгая:**
   - Останавливается при первом старом сообщении
   - Не проверяет дальше, даже если могут быть новые

### Вариант 1: Увеличить `max_check_before_stop`

**Текущее значение:** 20 сообщений  
**Рекомендуемое:** 100-200 сообщений

**Изменение в `channel_parser.py:3136`:**
```python

```

### Вариант 2: Изменить логику проверки

Вместо остановки после 20 старых сообщений:
1. Проверять до 100 сообщений
2. Если найдены новые — продолжать до конца батча
3. Если нет новых — остановиться после 100 проверок

**Текущий `limit`:** `batch_size * 100`  
**Рекомендуемый:** `batch_size * 500` для incremental режима
